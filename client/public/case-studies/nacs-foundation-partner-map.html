2025. Production-oriented partner data, map, and media-kit system.

Production-oriented build

The problem

A mission-driven team needed partner data ingested, mapped, maintained, and turned into usable program and media outputs. Location files arrived in inconsistent formats.

What I owned

I built the ingest, geocoding, map, and media-kit workflows, and I documented the engineering risks that should be closed before broader use.

What changed

The app is a single Express service for local running and for a Vercel serverless entry. Staff can upload CSV, spreadsheet, PDF, and document files. The app geocodes locations, draws a Leaflet map, and generates media kits. Records can live in Supabase or in a local JSON file.

How the team uses it

Staff upload a partner list, review locations on the map, and produce media materials from the same records. A public map is linked below. This case does not claim that every engineering risk has been closed in that deployment.

Deployment status

This is a production-oriented build: one Express app, file ingest, geocoding, a map, media-kit generation, and an optional database. It is not described here as a finished grant-management system. No grant outcome is part of this record.

Open risks named with the build:

  • An unauthenticated delete route for stores should be gated or removed.
  • Large upload limits increase the abuse surface on a public deployment.
  • Serverless in-memory sessions can fail when more than one instance handles the flow.
  • Any token that is not stored in the environment should be removed before production use.

System detail

  • Runtime: Node.js and Express, shared by local mode and Vercel.
  • Ingest: CSV, XLSX, PDF, and DOCX parsing, with Mapbox geocoding and a session-based review step.
  • Map: Leaflet and marker clustering.
  • Media kits: Sharp and canvas compositing.
  • Data: Supabase client and SQL migrations, or a local JSON fallback.
